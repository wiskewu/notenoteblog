什么是ADR

ADR（Architecture Decision Record）架构决策记录，是用于记录重大架构/技术选型决策等的标准化文档。

为什么要使用ADR

很多团队的文档常常陷入误区：只记录“代码做了什么”，从不记录“为什么这么做”。代码只能展示最终实现结果，但架构取舍、场景约束、舍弃的方案、预埋的技术债务，经常随着人员离职、时间迭代而彻底丢失，而ADR就是用于解决这个隐患。

什么时候使用ADR

所有反向修改成本极高、影响整体架构、长期生效的决策，都应该使用ADR进行记录，如：

  • 技术栈、框架、核心第三方依赖的选型；
  • 数据模型、数据库表结构核心设计方案；
  • 系统鉴权、安全、认证策略设计；
  • API架构选型（REST/TRPC等）；
  • 构建工具、部署平台、基础设施选型；
  • 影响用户侧的核心功能改版、架构重构；
  • 需要反复给团队新人、AI智能体解释的通用规则；

而那些“一次性买卖”的场景，则不需要使用ADR进行记录，如：

  • 直白易懂、无特殊逻辑的常规代码实现；
  • 一次性BUG修复、微小逻辑迭代；
  • 临时测试、废弃原型代码的逻辑；
  • 单纯UI、文案、样式微调；

ADR生命周期

ADR一旦落地，禁止删除和直接修改历史记录。

ADR拥有固定的生命周期：

PROPOSED（待提议） → ACCEPTED（已采纳） → SUPERSEDED（被替代） / DEPRECATED（已废弃）

关键规则：

  1. 历史ADR永久留存，用于追溯所有架构演变过程；
  2. 决策变更时，新建一篇ADR，标记旧ADR为「被替代」，并关联旧文档；
  3. 废弃的ADR仅作状态标记，不删除，不改动原文；

ADR规范

目录结构

所有ADR统一归档，项目全局唯一入口：

docs/
└── decisions/        # 官方推荐目录（也可统一用 docs/adr/）
    ├── README.md     # ADR 全局索引目录
    ├── ADR-001-xxx.md
    ├── ADR-002-xxx.md
    └── ...

命名规则

固定格式：ADR-序号-短横线小写标题.md

示例：

- ADR-001-use-postgresql-as-primary-db.md
- ADR-002-cache-consistency-strategy.md

README索引规范

必须维护索引文件，方便团队和 AI 智能体快速检索所有架构决策：

# 架构决策记录索引（ADR）
## 状态说明
- Proposed：待评审落地
- Accepted：正式生效执行
- Deprecated：已废弃停用
- Superseded：被新 ADR 替代

## 决策清单
| 编号 | 标题 | 状态 | 更新日期 |
| ---- | ---- | ---- | -------- |
| ADR-001 | 核心数据库选型方案 | Accepted | 2026-07-28 |

配套文档规范

ADR 是顶层架构记录，需要底层代码文档配合，形成完整闭环。

代码注释

在代码注释时，应只注释「为什么」，不注释「是什么」。

错误示例（重复代码，无意义）：

// 计数器+1
counter += 1;

正确示例（解释设计意图、特殊约束、规避风险）：

// 滑动窗口限流：窗口边界重置计数器，而非固定周期重置
// 规避边界突发流量击穿风险，详见 ADR-005 限流架构设计
if (now - windowStart > WINDOW_SIZE_MS) {
  counter = 0;
  windowStart = now;
}

禁止的文档陋习

  • 不写复述代码的无效注释
  • 不长期遗留空 TODO 注释（能改立刻改，不能改写入 ADR 待优化）
  • 不保留注释掉的废弃代码（Git 可追溯，无需冗余留存）

API文档规范

  • TS 项目优先使用类型注释 + 函数 JSDoc，标注入参、出参、异常、示例
  • REST 接口统一维护 OpenAPI/Swagger 文档
  • 所有特殊业务约束、接口设计逻辑，关联对应 ADR 编号

标准化的ADR模板

遵循官方 MADR / Nygard 通用规范，适配人工编写 + AI 生成，结构极简、信息完整，适配缺陷分析和架构复盘。

模板可以多种多样，下面举例说明：

# ADR-001：此处填写决策标题
## 状态
Accepted / Superseded by ADR-XXX / Deprecated
## 日期
2026-07-28

## 一、背景与问题 Context
描述当前项目现状、业务约束、技术瓶颈、规模限制（并发、数据量、运维人力、合规要求），清晰说明「为什么需要做这次决策」。

## 二、备选方案 Alternatives Considered
逐条列出所有评估过的方案，**必须包含优点 + 致命缺点 + 否决原因**：

### 方案1：XXX 方案
- 优点：xxx
- 缺点：xxx（重点写技术债务、潜在 Bug、性能风险、维护成本）
- 结论：采纳/否决

### 方案2：XXX 方案
- 优点：xxx
- 缺点：xxx
- 结论：采纳/否决

### 方案3：维持现状
- 优点：无改造成本
- 缺点：遗留问题持续存在，后续风险说明

## 三、最终决策 Decision
一句话明确最终选型，以及核心落地约束、执行规则。

## 四、正向收益 Consequences Positive
本次决策带来的业务、技术、效率提升，可量化优先量化。

## 五、负面代价与风险 Consequences Negative
【缺陷分析核心】
记录本次选型妥协的所有问题：编码隐患、性能瓶颈、运维成本、数据一致性风险、未来技术债务、已知坑点。

## 六、决策失效触发条件
明确什么场景下，当前架构决策不再适用，需要重构或替换。

## 七、关联文档
关联历史 ADR、接口文档、数据库设计、故障复盘记录

智能体Prompt示例

可以使用下述提示词，让AI智能体生成ADR：

请遵循 ADR 规范，使用标准 MADR 模板，为【具体技术选型/架构方案】编写正式 ADR。
要求：
1. 完整罗列备选方案、优缺点、否决理由；
2. 重点详细书写负面代价、潜在代码缺陷和技术债务；
3. 标注决策失效触发条件；
4. 使用 kebab 命名法，适配项目 docs/decisions 目录规范。

总结

  1. ADR时架构取舍的台账、技术债务清单、缺陷溯源手册；
  2. 只记录重大架构决策，不记录琐碎迭代，轻量化落地、长期维护；
  3. 历史 ADR 永不修改，仅新增、替代、标记状态，保证全链路可追溯；
  4. 重点书写备选方案缺点、选型风险、负面代价，为缺陷分析和 AI 迭代提供核心依据；
  5. 搭配规范的代码注释、API 文档、索引目录，形成完整的项目文档体系。
